# Methodology

This document explains what the benchmark measures, why it measures it that way, and what each choice rules in or out. Each module's docstring restates the part it implements. The tests in `tests/` check the parts where a silent mistake would change numbers, including that replaying configurations from cached scores gives exactly what MemMachine's EventMemory returns.

## 1. The question

Does reranking EventMemory's results with a cross-encoder (Qwen3-Reranker-8B) improve retrieval enough to justify its cost and latency? If the gain is marginal, the service could make reranking optional instead of on by default.

To answer that, the benchmark also measures how the gain depends on:
- the size of the units retrieved (EventMemory's segment length);
- whether the reranker scores the retrieved segments themselves or their expanded windows;
- how deep it reranks;
- how many tokens the reader LLM receives;
- the kind of question.

It also reports the reranker's own cost, and total cost over a continuous range of LLM prices.

LongMemEval-M is evaluated first. The other datasets prepared earlier are inactive until we decide which to add back (`rbench/datasets/__init__.py`).

## 2. What is measured

**No retrieved item is ever counted as a "hit".** Every measure is a per-query value computed from the gold. Reported numbers are means over test queries, each query weighted equally (a macro-average); nothing is pooled across queries. The full definitions are in the glossary at the top of `rbench/metrics.py`.

**Gold.** LongMemEval marks each turn that holds the answer (`has_answer`). A question's marked turns together are its one answer, and all of them are needed, so every-gold coverage is the headline measure (break-even, single-measure charts).

**Three readings of a gold turn.** Each is a separate metric, reported side by side and never combined:

| reading | a gold turn counts once… | use |
|---|---|---|
| complete | every segment of the turn has been read | strict; right for the short user turns (94% of the evidence, median 66 tokens) |
| touched | any segment of the turn has been read | a potential hit; LongMemEval's own notion of a retrieved unit; optimistic for long assistant turns (median 246 tokens) |
| fraction (recall) | — the share of the turn's characters read | between the two |

**Per query, at reader budget B:**
- first-gold coverage: some gold turn is read within B tokens (complete, or touched);
- every-gold coverage: every gold turn is read within B (complete, or touched);
- recall: the share of gold characters read;
- precision: the share of characters read that are gold;
- F1: computed per query, then averaged;
- the share of evidence turns found (`share`: complete; `share_touch`: touched): per query, the share of its evidence turns read within B, each turn counted once, averaged over queries (the user's decision, 2026-11-09, beside the others; every-gold stays the headline). With one evidence turn it equals every-gold; touched is generous on long assistant turns and complete is strict (`rbench/report/readings.py`);
- the same within the first k segments;
- coverage at equal counts instead of tokens: at the same vector search limit L (seeds retrieved), seeds kept after reranking k (contexts read), and segments read m (EventMemory's `max_num_segments`);

**Reader tokens are the tokens of the string EventMemory would hand the LLM** (`reading.py`):
- segments are admitted in EventMemory's order under a growing segment limit;
- the admitted set is rendered as EventMemory renders it: chronological components, one `[date and time] speaker:` header per run of a turn's segments, text as JSON;
- overlapping windows are counted once;
- a prefix costs the most any step up to it cost: the rendered string can shrink by a header when a segment joins two windows, but a reader that stops at the first segment that does not fit never gets there.

The cost is tracked incrementally with an additive token model: each segment's text, plus per run the tokens of that run rendered alone minus its text (the header, the quotes, the newline and the tokens that merge across those seams). Tests check it against a from-scratch recomputation (exact) and against tokenizing the rendered string; on real contexts of 4 LongMemEval-S histories (587 segment limits, 2026-11-10) the mean error is 0.19% and the largest 1.8%. Counting the header, quotes and newline apart instead overcounts by 1.7% on average with Qwen3's tokenizer, whose byte-level merges (`: "`, `."`) span the seams.

**Tokenizer.** Every token count in the benchmark uses Qwen3's tokenizer (`text.READER`; the user's decision, 2026-11-10): reader tokens (budgets, the token tables, fill depths, chart axes), segment sizes, reranker pairs and Qwen3-Embedding inputs. Qwen3-Reranker's and Qwen3-Embedding's tokenizers have the same 151,669-token vocabulary and count identically (checked). Why: one tokenizer across the benchmark, public, and no tokenizer is the reader's anyway (section 7). Billing is the exception, by necessity: each model bills in its own tokens, so an embedder's cost is counted with its own tokenizer (`Embedder.tokenizer`). Since the paid first stage became embeddinggemma (2026-11-11), `estimate` and `run` count its billed tokens with embeddinggemma's tokenizer, which is gated: they need a Hugging Face login (its input limit is never reached by LongMemEval's segments, so nothing else loads it). Until 2026-11-10 reader tokens were embeddinggemma's: on LongMemEval turns (10 histories each of S and M) Qwen3's tokenizer counts 2.1% fewer tokens, so a budget now holds about 2% more text than in earlier results.

**Which contexts are in the query result.** EventMemory's `string_from_query_result` restricts every context of the result to the admitted segments before joining components, so a window can link components even if the segment limit stopped before it. A reranked configuration's result holds all its L seeds (its vector search limit), so every window links from the start. The first stage without a limit reads as many seeds as the budget takes, and that count is its vector search limit, so a window links only once admission reaches it.

**Why there is no reader LLM and no judge.** An answering model adds its own variance and cost, and it mixes retrieval quality with reading skill. Coverage measures what retrieval controls. An end-to-end answer-accuracy check on a few final configurations remains possible if wanted.

## 3. The system under test: EventMemory, faithfully

The benchmark runs MemMachine's EventMemory itself, from the repository it lives in: a branch based on `feat/horizontal-scaling` (at `043fb7538` when it was branched; its changes since `bbcc8c3da` are partition handles and store plumbing, none of them in retrieval). Each history is encoded into its own partition in MemMachine's SQLite segment and vector stores (`rbench/memory.py`). The benchmark supplies only what a deployment supplies, as implementations of MemMachine's interfaces: an exact vector search engine, the embedder (MemMachine's `OpenAIEmbedder`) and a reranker that reads the score cache.
- **Segmentation:** MemMachine's `TextSegmenter` (LangChain's recursive splitter with EventMemory's separators, at most N characters), applied to each turn (event) separately. On 46,390 LongMemEval-M turns its output equals the separately pinned LangChain splitter's at every length tested. Option: the simple chunker (`cut<M>`, `memory.FixedCutSegmenter`), a Segmenter that cuts each turn every M characters regardless of content (the last piece shorter, nothing stripped); stage `lme-cut`. Recursive splitting at a limit of N gives segments well under N on average, so the simple chunker is size-matched rather than run at the same N (the user's request: "to normalize chunk sizes, recursive chunking may require some fitting"). `seg<N>` stays fixed, as production's splitter, and M is fitted before anything is embedded (`rbench/sizes.py`, `python -m rbench fit-cut`, CPU only; recorded in `config.CUT`). What is matched is the statistic the reports print as each chunking's measured size: per question, the mean characters per segment of the partition it searches, averaged over every question of the dataset. Characters, because both chunkers cut characters: at equal mean size the same text splits into about as many segments, so the index holds about as many vectors and a retrieved seed carries about as much text to the reranker and the reader (tokens follow; the reports print both, for the partitions searched and for the seeds retrieved). seg500 averages 299.2 characters per segment on LongMemEval-S, matched by cut354 (299.1), and 299.1 on LongMemEval-M, matched by cut355 (299.4). Equal mean size is not equal splitting of evidence turns: a cut every M characters splits every turn longer than M, where TextSegmenter keeps turns up to its limit whole. On LongMemEval-S's 100 proto questions (193 evidence turns), cut354 splits 23% of the evidence turns into several segments and seg500 5% (1.27 vs 1.09 segments per turn, measured 2026-11-09), so readings in full (every piece of a turn read) favour TextSegmenter, and touched readings (any piece) do not; chunker comparisons give both.
- **Events and their order:** speaker User or Assistant. EventMemory orders a partition by timestamp. LongMemEval dates sessions only to the minute, gives turns no time, and its files are not in date order (40 of 94 sampled M histories; most also have sessions starting in the same minute). So sessions are sorted by date (ties in file order), and each turn's timestamp is its session's date plus one microsecond per earlier turn in the history: every turn is ordered, and nothing rendered or embedded changes.
- **Embedding text** (`WholeTextDeriver`): `[<date>] <speaker>: "<JSON text>"`, so a session's segments embed differently in each history it appears in. Queries embed the question as it is. The paid stages embed with embeddinggemma-300m on DeepInfra (`gemma300m-di-raw`, no prompts; Qwen3-Embedding-8B until 2026-11-11, below); the free local runs use the same model on this machine's llama-server.
- **Embedding prompts (embeddinggemma, the comparison first stage):** the model card recommends `task: search result | query: ` for queries and `title: none | text: ` for documents; they are not required. MemMachine's sentence-transformers embedder uses only the query prompt (embeddinggemma's `default_prompt_name` is null), and its OpenAI-compatible embedder uses none. Four setups (`gemma300m`: both; `-q`: query only; `-raw`: none; `-d`: document only) are compared on the first stage alone over the first 200 questions of the sample order (the pilot's 100 and the next 100), and the best is used, since the strongest baseline tells the most about what a reranker adds. Telling them apart does not need whole histories: each question searches its evidence sessions plus 25 random other sessions of its own history, built exactly as the benchmark builds histories, and the setups are compared on how they rank the gold segments (`python -m rbench compare-embedders`, about half an hour locally instead of about 8 hours). Result on 200 questions (2026-11-06, `results/summary/embedders__longmemeval_m__seg500__200q__gemma300m.md`): the prompts make a small difference, seen at the top of the ranking. Taken as a 2 × 2 design (a framing chosen after a first look at the pilot's 100, which the 200 include, so this is not an independent replication), the query prompt makes it slightly worse (every gold turn in the top 5 segments −0.05, MRR −0.06, intervals excluding 0); the document prompt's effect (+0.01) cannot be told from none. The benchmark therefore embeds with no prompts (`gemma300m-raw`, `gemma300m-di-raw`), which is tied for best and exactly what MemMachine's OpenAI-compatible embedder sends. Choosing the setup on the evaluated questions can only flatter the first stage, which makes the reranker's measured gain conservative.
- **The embedder: embeddinggemma-300m on DeepInfra, no prompts** (`embedding.PAID = gemma300m-di-raw`; the user's decision, 2026-11-11, after the query grid below: "don't do 8B unless we can make it perform well"). $0.002 per million tokens, 768 dimensions (its own; nothing truncated), sent exactly as MemMachine's OpenAI-compatible embedder sends it. Its paid path was checked before the pilot (2026-11-11): 24 pilot segments and 3 questions through `memory.QueryCachingEmbedder` (MemMachine's OpenAIEmbedder) give the direct API's vectors (cosine 1.00000; DeepInfra's embeddinggemma is deterministic, unlike its Qwen3-8B), and the tokens billed equal ours (2,174). Embedding LongMemEval-M at 500 characters costs $1.16 (578.8M tokens, exact). The rest of this item is the Qwen3-Embedding-8B setup it replaces (the user's decision, 2026-11-09: production may use it), kept for any Qwen3 first stage. DeepInfra, $0.010 per million tokens, at 1,024 dimensions (Matryoshka; a vector truncated to its first 1,024 and re-normalized). Documents are embedded as EventMemory sends them, with no instruction; queries carry the model card's `Instruct: {task}\nQuery:` prefix unless compare-embedders shows the plain question does better (`qwen3-8b-di` / `qwen3-8b-di-raw`). Before anything is embedded at scale, `python -m rbench embed-checks` must pass (cents): the card's example scores reproduce within 0.005, a text embeds the same alone and in a batch, the 1,024-dimension vectors equal the truncated full ones, and billed tokens equal our count. Then `compare-embedders --embedders qwen3-8b-di,qwen3-8b-di-raw,gemma300m-di-raw` on the pilot's 100 reduced haystacks; if Qwen3 does not beat embeddinggemma, that is reported before going on. Embedding LongMemEval-M at 500 characters costs $5.68 (568.0M tokens, every distinct text counted, 2026-11-10) against embeddinggemma's $1.37, and its vectors are kept once, as float32, in the permanent copy: 32 GB at 1,024 dimensions, 116 GB at 4,096 (`costs.disk_bytes`).
- **Qwen3 on the pilot's 100, and the query grid (2026-11-11, EC2):** embeddinggemma beat Qwen3-Embedding-8B by a wide margin (MRR 0.653 against 0.447 with the card's instruction, 0.433 without; every@5 +0.24, intervals excluding 0), `results/summary/embedders__longmemeval_m__seg500__100q__qwen3-8b-di_qwen3-8b-di-raw_gemma300m-di-raw.md`. The vectors are sound (unit norms, the instruction applied, no collapsed or batch-position-dependent vectors); the gap is Qwen3 ranking Assistant replies above the user's own statements: the gold segments of 95 of the 100 questions are all User turns, Qwen3's top 5 are 63-92% Assistant by question type (embeddinggemma's 38-51%), and ranking User segments only, Qwen3 scores MRR 0.806 against embeddinggemma's 0.790. The card's task ("retrieve relevant passages that answer the query") plausibly favors replies that read as answers. The user's follow-up grid, on the query side only (documents unchanged, `[date] Speaker: "text"`): the user's instruction (`-mem`: "Given a user's query, retrieve relevant passages that provide the facts, preferences, or events needed to answer it.") beside the card's and none; the query as it is or rendered as the user's message (`-user`: `User: "<query>"`, exactly as EventMemory renders a turn, less the timestamp), for Qwen3 and embeddinggemma alike; and Qwen3-Embedding 0.6B, 4B and 8B (DeepInfra $0.010, $0.020 and $0.010 per million tokens, 2026-11-11), all at 1,024 dimensions. `compare-embedders --embedders` reports MRR by question type and each setup's share of Assistant turns in its top 5 beside the gold's. **Result** (200 questions, gemma300m-di-raw the reference, `results/summary/embedders__longmemeval_m__seg500__200q__20setups_5305a54e.md`): embeddinggemma (MRR 0.664; 0.668 with `-user`) and Qwen3-0.6B (best: no prompts, 0.677, +0.013 [−0.040, +0.064]) tie; every one of the 12 Qwen3-4B and -8B setups (6 each) trails by 0.19 to 0.28, intervals excluding 0 (best: 8B no instruction with `-user` 0.472, 4B with the user's instruction 0.470). The user's instruction lifts the 8B a little (0.452 to 0.470); `-user` halves embeddinggemma's Assistant share of the top 5 (0.48 to 0.23) with MRR unchanged and costs it on single-session-assistant questions (0.641 to 0.547). Across setups, embeddinggemma is the most robust (MRR 0.610 to 0.679 over its six setups, including the four prompt setups of 2026-11-06; the most even across question types). Width is not the cause: the 8B at 4,096 dimensions scores what it does at 1,024 (MRR 0.441 against 0.442, +0.001 [−0.027, +0.028]; keep 1,024; `results/summary/widths__longmemeval_m__seg500__100q__qwen3-8b-di.md`). **Diagnosis** (cached vectors, no further requests): every model ranks a segment of an evidence session first in 91–95.5% of questions (a random ranking: session MRR 0.235), so finding the session is easy on reduced haystacks and the models cannot be told apart there (8B 0.972 against embeddinggemma's 0.947; its two setups' intervals [−0.001, +0.052] and [+0.001, +0.049]). Within the session, 4B and 8B rank the assistant's on-topic reply above the user's statement: their top segment is wrong in 71–74% of questions (embeddinggemma 50%), 83–89% of those Assistant segments, about half of them the reply right after a gold turn. Gold turns are one segment in 93% of cases, while an Assistant turn averages 5.5 segments, so a reply puts several on-topic segments against one statement. embeddinggemma and 0.6B also score User segments about 0.05 higher on average than Assistant ones (the 8B about 0); with each speaker's mean score removed (a counterfactual), the 8B ranks about as well as embeddinggemma (0.45 against 0.46–0.51), the 4B worst. Reading each seed's neighbours (±1 segment) narrows the 8B's every@5 gap from 0.21 to 0.14; fusing the 8B with embeddinggemma (reciprocal ranks) is worse than embeddinggemma alone. Qwen3-Embedding's report describes one training recipe for all sizes, so no size is tuned differently; the 4B and 8B plausibly fit its retrieval notion of relevance (the passage that answers) more closely, which here is the reply rather than the evidence.
- **First stage:** `EventMemory.query` without a reranker, over the question's own history (~16k segments at 500 characters), with exact search: no approximate index, so no index recall loss is mixed into the result. Its vector search limit is 400 seeds, enough to fill the largest reader budget.
- **Expansion** (`expand_context` E; EventMemory's default is 0): MemMachine's own, E // 3 segments before the seed and the rest after, from its segment store. E = 1, 2, 3 and 6 are replayed.
- **Reranking:** Qwen3-Reranker in its model card's format, called as EventMemory calls any reranker: `score(question, contexts rendered with date and short time)`. With E > 0 EventMemory scores each seed's window (expand, then rerank). The pairs a paid run scores are collected by querying EventMemory with a reranker that records what it is asked. Replays read the cached scores; `tests/test_memory.py` checks that a replay at any vector search limit gives exactly `EventMemory.query`'s order.
- **Depth is the vector search limit:** EventMemory reranks every seed its vector search returns, so a reranked configuration reads only its reranked seeds. The first stage alone reads as many seeds as the budget takes, or, as `first_stage@nL`, only its top L, for comparison at the same vector search limit.
- **Reranker input format:** the model card's format (system prompt, instruction, query, document, empty think block). The user's rule was to use whichever of it and raw pairs does better on a small sample with the 0.6B. Raw pairs are what MemMachine's `CrossEncoderReranker` (a sentence-transformers CrossEncoder) sends: `tokenizer(query, text)`, which for Qwen3's tokenizer is the two texts concatenated (`rerankers.RAW_PAIRS`, scored the same way). Stage `format-test` compared them, free, on the local 0.6B over 100 LongMemEval-S questions (the M questions over smaller histories), reranking the same top L seeds at 500 characters (2026-11-09). The card's format won at every reading. At L 50, raw pairs read all evidence in full for 0.27 fewer of the questions at 500 reader tokens (95% interval [−0.39, −0.16]) and 0.25 fewer at 1,000 ([−0.36, −0.16]), and some evidence for 0.20 fewer at 500, falling below the first stage alone (0.26 vs 0.51 at 500); at L 20 the gaps are −0.13 and −0.19 at 500; at L 10 or past 2,000 tokens the two tie. Raw pairs cost about 40% fewer reranker tokens, but the card's format is what the benchmark uses, and the only one DeepInfra serves (it applies the format itself). A service that sends raw pairs to Qwen3-Reranker should expect results well below these.

**Processing is one history at a time.** Histories share sessions but not their dates, so nothing is shared across histories. Each history's stores are kept on disk; a history is encoded once, and one interrupted mid-way is encoded again: its vectors embedded before the interruption are reused from the permanent copy, keyed by the exact text (`memory.EmbeddingCache`), so only the rest is paid for. The copy is the only copy of every vector (the user, 2026-11-10: the vectors must survive a failure of EventMemory's storage layers): the benchmark's own vector store (`rbench/vectorstore.py`) keeps only records pointing into it, so re-encoding the same chunking and derivation from nothing costs no embedding even if every store is lost, and duplicate texts are paid once anywhere. **Back it up; never delete it to free disk**: that breaks every finished history and pays for the embeddings again. It stores float32, a row written once and never replaced; for LongMemEval-M at seg500 it is 32.1 GB at 1,024 dimensions (6,806,277 distinct texts for 7,568,164 segments: 10% of the segments repeat a text), about 68 MB per history; the stores add about 1.4 KB per segment, so a history takes about 91 MB in all (`costs.disk_bytes`, 42.9 GB for the core). The segment table the simulation reads (texts, order, token counts) is read back from the segment store and refreshed whenever the history is encoded again.

**The inactive datasets run through the same path** (`rbench/partitions.py`, `rbench/simulation.py`). A query searches one partition chosen by its dataset's scope: its own document (doc), its candidate documents (scope_docs: SWE-bench's repository snapshot), or the whole corpus (corpus, one partition every query shares). A document is an event with no producer (`NullContext`) and one text block, in corpus order; non-chat text has no author or time, so documents are embedded and rendered with no date (`FormatOptions(date_style=None, time_style=None)`): the embedding text, the reranker's input and the reader's context are the segment's JSON text alone. Gold is character spans in event texts (LongMemEval's gold turns are whole-turn spans). Each segment's offsets in its event are found in order, since TextSegmenter's segments are its text's substrings with edge whitespace stripped; a span is trimmed to its non-whitespace extent and maps to the segments overlapping it. On every query of the seven datasets, at seg500 and cut500, every gold span maps to segments, none empty (`tests/test_partitions.py` checks the tiny samples). In a corpus partition a window can reach across a document boundary into the neighbouring document, as EventMemory's expansion does whenever documents share a partition. Where a window joins consecutive segments of one event, EventMemory concatenates them, so whitespace TextSegmenter stripped at a boundary is lost from the rendered text (production behaviour; the gold mapping is unaffected).

## 4. What is varied, and what is replayed for free

| factor | values | how |
|---|---|---|
| segment length | 500 characters (core); 250, 1,000, 2,000 | one embedding per length |
| chunker | EventMemory's TextSegmenter (`seg<N>`); the simple chunker size-matched to it (`cut<M>`, M fitted: cut355 for LongMemEval-M's seg500; optional stage `lme-cut`) | one embedding per chunking |
| reranking | none; rerank the seeds; rerank each seed's window (expand, then rerank) | seeds scored; windows scored at `expand_context` 3 |
| reading (`expand_context`) | the seeds (0), or their windows at 1, 2, 3, 6 | replayed; free except expand-then-rerank, which needs its windows scored |
| rerank depth = vector search limit L | every L up to the pool, fixed at 200 seeds and 100 windows ("Pool depth" below, with what each reaches); the whole pool is scored, so 5, 10, 20 (EventMemory's default), 30, 50, … up to the pool replay | replayed from cached scores |
| first stage's vector search limit | the same L values, or none (as many seeds as the budget reads) | replayed |
| reader budget | continuous: every ranking is read to the end of its pool, so no curve stops short of its plateau (500–4,000 tokens is the realistic range); charts mark every 500, recall and precision are measured every 250 up to 16,000 | replayed |
| seeds kept (k), segments read (m) | any count | replayed |

**Pool depth.** The pools are fixed: the reranker scores the top 200 seeds, or the top 100 windows when it scores windows (expand, then rerank), at every segment length, chunker and sample (`config.EVAL.pool_seeds`, `pool_windows`; the user's decision, 2026-11-10: "just do L100 and L200"). An earlier rule measured a pool deep enough to fill the reader-token axis for 95% of questions; that margin was not the user's (their 0.95 was about the curve's recall) and gave arbitrary-looking limits (221, 116). What a pool reaches is measured and reported beside it (`rbench/depth.py`): for how many questions reading it reaches the axis end (16,000 reader tokens), and for how many it holds all the evidence (the ceiling no reading of it can pass). At 500 characters on LongMemEval-S (100 questions, reader tokens counted with Qwen3's tokenizer, 2026-11-10), 200 seeds sit below the measured fill depth for 95% of questions (234; 221 when counted with embeddinggemma's), and reading them reaches 16,000 tokens for 61% of the questions. At shorter segments the same pool holds less text (at 250 characters about half), so reading it ends before 16,000 tokens and the curves level off earlier, which is accepted (the user, 2026-11-09: "limit to 16k tokens or less"); a stage can set its own pool (`grid.Run.pool_seeds`). `estimate` reports both shares beside each pool, and the charts' bound line shows the ceiling: where it levels off below 1, the remaining evidence is outside the pool. The bound (`rbench/bounds.py`) is the cheapest reading of the same pool any ranking could achieve, exact with seeds alone (expand_context 0). With windows no bound is drawn: an exact one isn't computable here (a segment that joins two windows can save a header, so the rendered cost is not monotone in what is read), and a valid floor (the evidence's own text plus one header) was exact for no question, so it said nothing (the user's decision, 2026-11-09).

Units follow EventMemory's settings: segment length in characters, `expand_context` and the vector search limit in counts. Tokens measure what things cost: reader budgets, reranker input, and the first stage's head (16,384 tokens of seed text, enough to fill the largest budget). Pools and depths are seed counts rather than tokens because the vector search limit is a count; equal reranker input across segment lengths is compared through each configuration's measured reranker tokens (§5 of the report). A segment length is a limit, not a size: the simulation records each history's measured mean segment (characters and tokens) and the mean unit each configuration reads (the seed, or its window), and the reports state those measured sizes. Where a comparison pairs units by size (the expansion comparison, §11), it pairs by measured size and flags pairs further apart than `config.EVAL.size_tolerance` (25%).

Qwen3-Reranker scores each pair independently, so a pool scored to depth D answers every shallower depth exactly. The first stage runs once per question, deep enough for every configuration. (A real vector index asked for the top 20 may return slightly different results from the top 20 of a deeper search, but that is an index effect outside this evaluation.)

**Break-even.** Scaling both prices by the same factor changes no decision, so whether reranking pays depends only on the price ratio. For each every-gold coverage target:
1. choose the cheapest configuration without a reranker (any segment length and expansion) and the reranked configuration that pays off at the lowest ratio (seeds or windows reranked, any expansion, depth and segment length);
2. compute r* = reranker tokens ÷ reader tokens saved;
3. bootstrap questions for a 95% interval, each resample making its own choice in step 1.

Budgets are exact: a target's budget is the order statistic of the per-question costs, not a grid point.

There is no dev split (§6), so the choice and the measurement use the same questions. The minimum over many more reranked than unreranked configurations leans optimistic for the reranker; the interval includes the selection's variability.

**Latency.** Call times are recorded as a by-product only and reported in §17. They do not represent a self-hosted deployment (DeepInfra requests run concurrently under an adaptive limit, with queueing and any retries), and nothing is spent to measure them. **Throughput** (`rbench/limits.py`): each hosted model (each reranker, and the embedder) has its own limit on requests in flight, starting at 16, growing while requests succeed and cut on 429s, capped at 150 below DeepInfra's default of 200 concurrent requests per model; price is per token, so this changes time, not cost. Retryable failures (429, 5xx, timeouts) back off up to 5 minutes and keep trying for an hour per request, then the run stops with a message to rerun; out of credits and non-retryable errors stop at once (`rbench/credits.py`). A hosted reranker scores each history's pairs while the next histories embed (`pipeline.prepare_and_score`): once a history is stored, the same thread measures its questions' depths and runs EventMemory's query in record mode, so every engine call stays sequential, and a background thread per model only talks to DeepInfra and the score cache. The pools are fixed, so each question is scored to its whole pool while the next histories embed, and nothing is scored that a sequential run would not; a run prints what was scored while embedding.

**Settings are chosen overall, never per question** (the user's rule, 2026-11-09). Every choice the reports make (the vector search limit, seeds kept, segment length, expansion, scoring position, and each side of the cost comparison) is made once for all questions at a given reader budget or coverage target, because a service runs one configuration. The pool rule is overall too: a depth that fills the axis for 95% of the questions. The only per-question optima are the true bounds (`rbench/bounds.py`), labelled as bounds.

## 6. Statistics

- **No split** (decided 2026-11-06): all 470 questions are evaluated. Samples take questions in a fixed hash order, so the pilot's 100 are part of the core's 470.
- **Selection:** choices among configurations are made and measured on the same questions; where a choice is reported (§5–6 of the report), the report says so.
- **Intervals:** 95% paired bootstrap intervals resample questions (1,000 resamples). Histories are independent: evidence sessions are essentially unique to their question, with 8 of 940 shared.
- **Many comparisons:** single intervals that just exclude zero are hypotheses. Conclusions need patterns that hold across segment lengths and question types.

## 7. Threats to validity

| threat | handling |
|---|---|
| A reranker can only reorder what the first stage retrieved | the headroom table (§2 of the report) gives, per vector search limit, how often all of a question's evidence is among the seeds retrieved; the coverage charts show the first stage cut to the reranker's limit beside the reranker |
| Choosing the best of many configurations on the same questions flatters the winner | stated with every chosen number; bootstrap resamples re-choose; conclusions rest on patterns across segment lengths and question types |
| LongMemEval's timestamps are minute-level and its files out of date order | sessions sorted by date, turns ordered by unrendered microsecond increments (§3); tests check the order is EventMemory's |
| Whole-turn gold is strict for long assistant turns | complete, touched and fraction are reported separately |
| Questions and evidence sessions involve LLM generation | human-rewritten and human-screened; filler is real user–assistant chat (ShareGPT, UltraChat) |
| The simulation might not match EventMemory | it runs MemMachine's EventMemory; the two replayed pieces (admission at every segment limit, the reader-cost model) are tested against `build_query_result_context` and `string_from_query_result`, and replayed reranking against `EventMemory.query` |
| Token counts differ between tokenizers | every count is Qwen3 tokens (reader budgets, segment sizes, reranker pairs, embedding inputs); an LLM bills in its own tokenizer, so budgets are a yardstick, not an exact bill (on LongMemEval turns embeddinggemma's tokenizer counts 2.2% more) |
| Spend | No cap in the code (the user's decision, 2026-11-09): the prepaid DeepInfra credits are the cap, with auto top-up off. `estimate` prices embedding and reranking (embeddinggemma: $1.16 at 500 characters on LongMemEval-M, Qwen3-Embedding-8B $5.68; every distinct text not yet in the permanent copy counted), and the user approves the price before any paid run. Out of credits, a run stops cleanly (`rbench/credits.py`): every reranker request is cached as it returns, and a partition whose embedding stopped has no done marker, so the rerun deletes and re-encodes it; `tests/test_credits.py` runs out mid-reranking and mid-ingest and checks the rerun. The call logs record what each run spent |
| Interruptions and failures | reranker scores are saved as each request returns; a history's embeddings are cached by text as each request returns, so a history interrupted mid-way is encoded again paying only for what was never embedded; reruns skip finished work. The first Ctrl-C sends nothing more and lets the requests in flight finish and be cached; out of credits, an hour of failures and a full disk stop with a message saying how to resume. Every file is written whole or not at all (a temporary file moved into place: indexes, segment tables, depths, results, vectors), and an index is rewritten only when it changed. Every SQLite database waits up to 30 s for a lock and runs with a write-ahead log, NORMAL sync and full fsync (macOS's fsync does not flush the drive without it), so a power cut can lose the last few writes but not corrupt a store. A history's files are checkpointed (their logs written into the files and fsynced) before its done marker is written, itself atomically, so a power cut never leaves a history marked done with writes lost; a history whose vectors are missing anyway says to delete its marker and rerun. One process per store: MemMachine's SQLite vector store replays and saves every partition it holds, so a second process could overwrite a partition another is writing; a lock makes the second one stop at once. Embedding requests stay under MemMachine's 75,000-character call cap, so it never splits one; a stage refuses to start when its new stores would not fit the free disk |
