# rbench: is cross-encoder reranking worth it for EventMemory?

This benchmark measures what Qwen3-Reranker-8B adds to EventMemory's retrieval on LongMemEval-M, against what it costs. It covers:
- equal reader tokens, equal reranker cost, equal total cost over a continuous range of LLM prices, and equal counts (vector search limit, seeds kept, segments read);
- segment length;
- reranking the retrieved segments vs. their expanded windows (`expand_context` 0, 1, 2, 3, 6; windows reranked at 3);
- rerank depth;
- question type.

The first-stage results come from the same runs, so the benchmark doubles as an embedding and segmentation benchmark.

- **[METHODOLOGY.md](METHODOLOGY.md):** what is measured and why, the design, statistics and threats to validity. Start here.
- **[DATASETS.md](DATASETS.md):** measured profiles and justifications; generated by `python -m rbench profile`.
- **Metrics:** every metric is a per-query value over gold turns (complete, touched or fraction), averaged over queries. Nothing is counted as a "hit". Every-gold coverage (all of a question's evidence read) is the headline. The glossary is at the top of `rbench/metrics.py`.
- **No dev split:** all 470 questions are evaluated; configuration choices are made on the same questions, and the report says so where it makes one.

## Pipeline for history datasets (LongMemEval)

| stage | module | output (cached; reruns skip finished work) |
|---|---|---|
| prepare | `rbench/datasets/longmemeval.py` | `data/prepared/longmemeval_m/` — one file per history; gold turns and sessions |
| ingest | `rbench/histories.py`, `rbench/memory.py` | each history encoded into its own EventMemory partition: MemMachine segments, derives and embeds it; stores kept under `data/memory/<embedder>/<dataset>/seg<N>/` |
| query | `rbench/simulate_histories.py` | `EventMemory.query` per question and `expand_context` (exact search, MemMachine's own expansion) |
| rerank | `rbench/rerankers.py`, `rbench/memory.py` | what `EventMemory.query` sends its reranker, collected by querying with a recording reranker; every pair cached by content |
| simulate | `rbench/simulate_histories.py`, `rbench/reading.py`, `rbench/metrics.py` | one row per question × ranker × depth × expansion; a reranked row reads only its pool; reader cost = tokens of EventMemory's rendered context |
| report | `rbench/report/` | `results/summary/…md`, `results/figures/…png` |

The benchmark lives in MemMachine's repository (`evaluation/reranker/`, on a branch based on `feat/horizontal-scaling`) and runs that branch's own EventMemory: `packages/server` and `packages/common` are path dependencies, so any change to EventMemory the benchmark needs is in the same diff. `rbench/memory.py` supplies only what a deployment supplies, as implementations of MemMachine's interfaces: an exact vector search engine, the embedder (MemMachine's `OpenAIEmbedder`, against the local server or DeepInfra) and a Qwen3 reranker that reads the score cache. `tests/test_memory.py` checks that replaying reranked configurations from cached scores gives exactly the order of `EventMemory.query` at every vector search limit, and that the admission replay and reader-cost model match `build_query_result_context` and `string_from_query_result`.

## Running

From `evaluation/reranker/`:

```sh
uv sync
.venv/bin/python -m pytest -q tests
.venv/bin/python -m rbench prepare longmemeval_m longmemeval_s   # download and split into histories
.venv/bin/python -m rbench run lme-test                          # free: local, 8 LongMemEval-S histories
.venv/bin/python -m rbench estimate lme-core lme-sizes lme-depth --embedder gemma300m-di-raw
.venv/bin/python -m rbench show longmemeval_s --sample tiny --chart coverage,rpf   # zoomable chart windows from saved results
```

**Adding a model to compare** takes one entry in `RERANKERS` (`rbench/rerankers.py`): its backend and price, its chart label, color and marker, and its template (what it reads around each pair). Then run any stage with `--models`, e.g. `run lme-core --models q4,q8 --max-usd 2`; the report and charts include every registered model that has scores.

Paid runs on DeepInfra need a key in `.secrets/deepinfra_api_key`. `--max-usd` caps total DeepInfra reranker spend across all models and runs, read from the call logs: it stops before a request group would pass the cap, and never changes what runs. Embedding spend is not capped (see the table). Interrupted runs lose almost nothing: reranker scores are saved per request, each history is encoded (embedded) once and one interrupted mid-way is encoded again, and a rerun skips finished work. Preflight first (METHODOLOGY.md §8):

```sh
.venv/bin/python -m rbench smoke
.venv/bin/python -m rbench embed-fidelity
.venv/bin/python -m rbench run lme-pilot --max-usd 3 --embedder gemma300m-di-raw
.venv/bin/python -m rbench run lme-core  --max-usd 6 --embedder gemma300m-di-raw
```

## Cost (DeepInfra list prices, 2026-11-06; estimates from `estimate`)

| stage | what | reranking (8B) | embedding |
|---|---|---|---|
| lme-pilot | 500-character segments, 100 questions, top 50 seeds (reused by core) | ~$0.15 | ~$0.30 (part of core) |
| lme-core | 500-character segments, 470 questions, top 50 seeds and their windows | ~$0.68 | ~$1.37 |
| lme-sizes | 250 / 1,000 / 2,000 characters, top 50 seeds and windows | ~$2.80, likely more | ~$4.09 |
| lme-depth | 500-character segments, top 200 seeds | ~$2.70 (about $2 beyond core) | — (core's vectors) |
| **total** | | **~$5.50–6.50** | **~$5.50** |

Before the histories are encoded, `estimate` probes random seeds; retrieved seeds run longer at long segment lengths, so lme-sizes may cost more than shown. Once they are encoded, `estimate` counts the exact pairs still to score.

Disk: keeping every history's vectors takes ~12 GB at 500 characters (float16); the four lengths together are estimated at 40–50 GB.
