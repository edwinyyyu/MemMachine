# rbench: is cross-encoder reranking worth it for EventMemory?

This benchmark measures what Qwen3-Reranker-8B adds to EventMemory's retrieval on LongMemEval-M, against what it costs. It covers:
- equal reader tokens, equal reranker cost, equal total cost over a continuous range of LLM prices, and equal counts (vector search limit, seeds kept, segments read);
- segment length;
- reranking the retrieved segments vs. their expanded windows (`expand_context` 0, 1, 2, 3, 6; windows reranked at 3);
- rerank depth;
- question type.

The first-stage results come from the same runs, so the benchmark doubles as an embedding and segmentation benchmark.

- **[METHODOLOGY.md](METHODOLOGY.md):** what is measured and why, the design, statistics and threats to validity. Start here.
- **[results/README.md](results/README.md):** the reports and charts of every run, each report opening with a summary (generated after each run).
- **[DATASETS.md](DATASETS.md):** measured profiles and justifications; generated by `python -m rbench profile`.
- **Metrics:** every metric is a per-query value over gold spans (LongMemEval's gold turns, whole; complete, touched or fraction), averaged over queries. Nothing is counted as a "hit". Every-gold coverage (all of a question's evidence read) is the headline. The glossary is at the top of `rbench/metrics.py`.
- **No dev split:** all 470 questions are evaluated; configuration choices are made on the same questions, and the report says so where it makes one.

## Pipeline (every dataset)

| stage | module | output (cached; reruns skip finished work) |
|---|---|---|
| prepare | `rbench/datasets/` | `data/prepared/<dataset>/`: documents (or LongMemEval's histories), queries and gold |
| ingest | `rbench/partitions.py`, `rbench/memory.py` | each query's partition encoded into EventMemory: a LongMemEval history (turns as events, `rbench/histories.py`), the query's document, its candidate documents, or the whole corpus (documents as events with no producer or date). MemMachine segments, derives and embeds it; stores kept under `data/memory/<embedder>/<dataset>/<chunking>/` (`seg<N>`: MemMachine's TextSegmenter; `cut<N>`: the simple chunker) |
| query | `rbench/simulation.py` | `EventMemory.query` per query and `expand_context` (exact search, MemMachine's own expansion) |
| rerank | `rbench/rerankers.py`, `rbench/memory.py` | what `EventMemory.query` sends its reranker, collected by querying with a recording reranker; every pair cached by content |
| simulate | `rbench/simulation.py`, `rbench/reading.py`, `rbench/metrics.py` | one row per query × ranker × depth × expansion; a reranked row reads only its pool; reader cost = tokens of EventMemory's rendered context; gold = character spans in event texts (LongMemEval's turns whole) |
| report | `rbench/report/` | `results/summary/…md`, `results/figures/…png` |

The inactive datasets run through the same path on request: `python -m rbench adhoc --datasets qasper,nq --chunkings seg500 --models q06-local --sample tiny`.

The benchmark lives in MemMachine's repository (`evaluation/reranker/`, on a branch based on `feat/horizontal-scaling`) and runs that branch's own EventMemory: `packages/server` and `packages/common` are path dependencies, so any change to EventMemory the benchmark needs is in the same diff. `rbench/memory.py` supplies only what a deployment supplies, as implementations of MemMachine's interfaces: an exact vector search engine, the embedder (MemMachine's `OpenAIEmbedder`, against the local server or DeepInfra) and a Qwen3 reranker that reads the score cache. `tests/test_memory.py` checks that replaying reranked configurations from cached scores gives exactly the order of `EventMemory.query` at every vector search limit, and that the admission replay and reader-cost model match `build_query_result_context` and `string_from_query_result`.

## Running

From `evaluation/reranker/`:

```sh
uv sync
.venv/bin/python -m pytest -q tests
.venv/bin/python -m rbench prepare longmemeval_m longmemeval_s   # download and split into histories
.venv/bin/python -m rbench run lme-test                          # free: local, 8 LongMemEval-S histories
.venv/bin/python -m rbench estimate lme-pilot lme-core               # the minimal paid run; uses Qwen3-Embedding-8B
.venv/bin/python -m rbench show longmemeval_s --sample tiny --chart coverage,rpf   # zoomable chart windows from saved results
```

**Adding a model to compare** takes one entry in `RERANKERS` (`rbench/rerankers.py`): its backend and price, its chart label, color and marker, and its template (what it reads around each pair). Then run any stage with `--models`, e.g. `run lme-core --models q4,q8`; the report and charts include every registered model that has scores.

Paid runs on DeepInfra need a key in `.secrets/deepinfra_api_key`. There is no spend cap in the code: the prepaid DeepInfra credits are the cap, so turn off DeepInfra's auto top-up, and `estimate` is the price check before a run. Out of credits, a run stops with "DeepInfra is out of credits: top up and rerun; finished work is kept", and the same command resumes after a top-up (`rbench/credits.py`). Each run ends by printing what it spent, from the call logs. Hosted models run as many requests at once as DeepInfra allows (an adaptive limit up to 150 per model), and a hosted reranker scores each history while the next ones embed; `estimate` also gives the disk the new stores take (METHODOLOGY section 5, "Throughput"). Interrupted runs lose almost nothing: reranker scores are saved per request, each history is encoded (embedded) once and one interrupted mid-way is encoded again, and a rerun skips finished work. Preflight first (METHODOLOGY.md §8):

```sh
.venv/bin/python -m rbench smoke
.venv/bin/python -m rbench embed-checks
.venv/bin/python -m rbench compare-embedders --embedders qwen3-8b-di,qwen3-8b-di-raw,gemma300m-di-raw
.venv/bin/python -m rbench run lme-pilot
.venv/bin/python -m rbench run lme-core
```

## Cost

The pools are fixed: the reranker scores the top 200 seeds, or the top 100 windows (`config.EVAL.pool_seeds`, `pool_windows`; the user's decision, 2026-11-10), at every segment length, and every shallower vector search limit replays for free. `estimate` prices each stage at them and reports, beside each pool, for how many questions reading it reaches the reader-token axis end (16,000) and for how many it holds all the evidence (`rbench/depth.py`). At shorter segments the same pool holds less text, so the curves level off earlier.

Priced 2026-11-10 for the 8B at DeepInfra's $0.05/M (`estimate lme-core lme-sizes lme-cut`), before the paid embeddings exist: pair tokens probed on 8 LongMemEval-M histories per chunking; `estimate` re-prices exactly once the histories are embedded.

| stage | reranking | embedding (Qwen3-Embedding-8B) | total | disk |
|---|---|---|---|---|
| lme-pilot + lme-core, the minimal run (seg500, seeds: 8B $0.84, 4B $0.42) | $1.26 | $6.29 | **$7.55** | 58 GB |
| lme-windows (expand, then rerank at x3, 8B) | $0.94 | shared with the core | $0.94 | 0 |
| lme-sizes (seg250, seg1000, seg2000; 8B seeds and windows) | $7.17 | $18.75 | $25.92 | 166 GB |
| lme-cut (cut355; 8B seeds and windows) | $1.80 | $6.48 | $8.28 | 58 GB |
| all four | $11.17 | $31.52 | $42.69 | 282 GB |

Disk counts the index, the stores, the segment tables and the kept embedding cache (float32, as the API returns it). Every stage together needs about 282 GB, more than the 264 GB free on 2026-11-10: the minimal run fits; the others need space freed first (`run` refuses to start when the new stores would not fit).

On 8 locally embedded LongMemEval-M histories at seg500, reading 200 seeds reaches 16,000 tokens for all 8 and holds all the evidence for 7 of 8; 100 windows reach it for all 8 and hold all the evidence for all 8. The pilot (100 questions) is part of the core. The 4B costs half the 8B's price, the 0.6B a fifth. Longer segments cost more to rerank at the same pool (each pair is longer): seg2000's seeds are $1.34, against $0.84 at seg500.

Embedding costs more than reranking (Qwen3-Embedding-8B at $0.010/M; embeddinggemma was about $1.37 per length). The minimal run (the user's decisions, 2026-11-09 and 2026-11-10) is the pilot and the core, about $7.55: seg500, the seeds scored by both the 4B and the 8B, no windows scored, plus the checks; disk about 58 GB with the kept embedding cache. `lme-windows` is optional. `lme-sizes` and `lme-cut` stay in the plan, unscheduled. The simple chunker is size-matched to seg500 (cut355 on LongMemEval-M: its length fitted so the mean segments match, METHODOLOGY section 3).

Disk (`estimate` gives it per stage, 2026-11-10, LongMemEval-M with Qwen3-Embedding-8B's 1,024 dimensions: float16 index, segment store, segment tables): about 26 GB at 500 characters (lme-core; the size-matched cut355 the same), 48 GB at 250, 16 GB at 1,000 and 11 GB at 2,000 (lme-sizes 76 GB), so about 128 GB for every planned stage.
